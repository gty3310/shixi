# ADR-0001：练习统计采用单一事实源（事件账）＋读时派生＋单写入口

## Status

Accepted（2026-11-26，用户拍板；重构分阶段落地中，任务清单见 `docs/pass-ledger-refactor/TASKLIST.md`）

## Context

弦歌的遍数统计长期由两本互不感知的账并行维护：

- `records.json`（`Store`）：按「日期 → 曲目」记次数，另有 `Track.baseTotal` 历史偏移；
- `chapter_stats.json`（`ChapterStatsStore`）：按「书 × 章 × 日期」记次数，分自动（a）与手动（m）两路。

两本账没有任何对账或派生关系。自动写入有四条互不联动的路径（整轨播完 `handleTrackCompletion`、250ms 采样跨章 `chapterStep`、跟读完成 `finishFollowPass`、阅读页「已读到末尾」按钮），手动写入另有四处（主页步进器、篇行 chip 编辑器、章列表页补记／整本 ±1、计划页手动达标，后者还自带第三份数据 `PlanData.manualEntries`）。展示面有五个以上，各读各的账：《论语》篇行甚至同行混读两账——「今日 X 遍」chip 读分章账、同行统计小字读 records 账。

2026-11-26 用户真机暴露两个症状，排查（代码＋数据＋截图三方一致）定案为同一结构病：

1. **自相矛盾**：《论语》陽貨第十七篇行显示「今日 2 遍」，同行统计却是「本周 0 遍 · 本月 2 遍」。两本账不一致时，同一行两个数字必然打架。
2. **漏记**：整本书播完，唯独第 17 篇不自动增加遍数。该篇末句结束时间恰等于整篇时长，播放中采样无法越界计数，只能靠整轨播完兜底；而兜底前置条件苛刻，且可被念注「押后完成」在用户打断时整笔作废。此外已定案的分叉还有：阅读页单章循环回绕时分章账 +1 但 records 的播完事件永不触发；跟读路径只写 records、从不写分章账。

业界对此类错误有明确命名：**dual write（双写）＋把派生数据当独立事实源**（Kleppmann《Designing Data-Intensive Applications》Part III：system of record 中每个事实恰好表示一次，派生数据丢了必须可重建；其 2015 年文指出双写产生的不是「最终一致」而是可能永久不一致）。本仓两本账正是同一事实（一次练习）的两种聚合，却被做成两本独立增量账——出入时没有任何一方有资格说自己是对的。调研全文存于内部调研报告（2026-11-26，《避免「双份事实源」状态漂移 Bug》）。

## Decision

1. **单一事实源**：新建只追加的练习明细（事件账）`pass_events`：一次完成练习＝一条事件 `{日期, bookId, chapterIndex, trackId, 来源 auto/manual, dedupKey}`。`records.json` 与 `chapter_stats.json` 退役为该事件账的派生视图；`Track.baseTotal` 与已删曲目的历史在迁移时各转成一条期初事件，信息不丢。
2. **统计一律读时派生**：曲目数、章节数、今日／本周／本月／累计、整本遍数，全部由同一聚合函数对明细按同一时间字段与同一窗口常量计算，不再存储任何增量计数。个人规模（万级明细）下全量聚合为毫秒级，不预设缓存；将来若实测需要缓存，缓存必须可丢弃重建并带对账。
3. **单写入口**：所有「一遍完成」的判定收敛到唯一记账入口（`PassCounter`）：普通播完、跟读播完、单章回绕、跨篇续播、章级播放、念注押后完成，全部**先记账、再决定去向**——念注可以押后「去向」，永不押后「计数」；用户中途打断已完成的遍，账不回滚。手动改数（四处）统一改走同一入口写 manual 事件。
4. **幂等去重**：每条事件带稳定 dedupKey（如 sessionId＋chapterId），写入按 key 去重；完成判定单点化（章完成只认采样判定一处，曲目完成由章完成聚合派生），不再让 MediaPlayer 播完事件与采样判定各判一次。
5. **不变式护栏**：四条不变式（今日 ≤ 本周 ≤ 累计；Σ各章 == 曲目总数，整曲播放记入显式「整曲」桶；派生统计 == 从明细重算；计数 ≥ 0 且 dedupKey 唯一）写成自动测试与 debug 启动自检；另设 grep 级适应度检查（`tools/check_single_writer.sh`），基线外新增写入点即报警。

## Consequences

- 正面：漏记、错记、两处对不上在结构上失去存在前提；以后新增任何播放模式只需接一个入口，不再逐路径打「让位／押后／兜底」补丁；历史可审计、可重建（事件账即版本控制式的提交日志）。
- 代价：约三个版本的分步重构（快照→事件账与迁移→入口收敛→展示派生→测试与对账），每步可回退；迁移时个别篇的历史总数会跳变——那正是现在两本账打架的存量差，迁移口径（同日同篇两账自动数取较大者、手动数保留来源、旧文件改名留档）写在任务清单中，发版说明须向用户交代。
- 约束：本决策被 `AGENTS.md` 红线一引用；`tools/check_single_writer.sh` 在重构期以基线模式守住「不再新增写入点」，重构完成后收紧为「入口之外零写入点」。

## 被否决的方案

- **双计数器＋逐点打补丁**（给回绕路径补一行 records 自增、把播完兜底的严格不等式改成 ≤、念注改先计数后押后）：每处都是小时级、当下能绿灯，但只堵已知的三个洞。五类分叉面（章末恰等于时长、单章回绕不产生播完事件、跟读接管播完、念注押后播完、识读挂起采样）与未来新播放功能仍会继续产新洞；且两本账的手动改数漂移（只改一本）永远存在。更重要的是，用户 2026-11-26 已定铁律：改 bug 永远做系统性修复、禁止补丁止血（见 `AGENTS.md` 红线二）。故否决。
- **完整事件溯源框架／CQRS 双库**：对单人单机 App 是过度工程；一张只追加的明细表即可获得事件溯源的全部实际收益（可重建、可审计、可修正），不引入需要被维护、被保持一致的新组件。
